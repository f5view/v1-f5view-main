# Marketplace — консольный маркетплейс на Go

## О чём проект

Ты пишешь маленький консольный маркетплейс: программа читает команды из stdin, хранит товары (листинги) и отвечает в stdout. Хранилищ два — в памяти и в JSON-файле, и переключаются они флагом при запуске, а не переписыванием кода.

Смысл проекта не в маркетплейсе, а в том, чтобы руками прочувствовать четыре базовые вещи Go: структуры и методы, интерфейсы как способ подменять реализацию, работу с ошибками и файловый I/O с JSON. Всё делается на стандартной библиотеке.

## Чему научишься

После сдачи ты должен понимать и уметь объяснить вслух:

- **Структуры и методы.** Когда нужен value receiver, а когда pointer receiver, и что происходит с копированием при вызове.
- **Интерфейсы.** Зачем они нужны и как через интерфейс подменить хранилище (память ↔ JSON), не трогая код, который его использует.
- **Ошибки.** `errors.New`, `fmt.Errorf` с `%w`, `errors.Is`, `errors.As`. Чем `%w` отличается от `%v`.
- **Файлы и JSON.** `os.ReadFile`, `os.WriteFile`, `encoding/json`. Атомарная запись через временный файл и `os.Rename`.

## Нефункциональные требования

- Только стандартная библиотека. Сторонние пакеты не нужны и не приветствуются.
- Код собирается командой `go build .` из корня репозитория. Имя бинаря любое, дальше в тексте он называется `marketplace`.
- Код проходит `gofmt`, `go vet` и `golangci-lint` с конфигом из репозитория.
- Программа не падает на плохом вводе. Любая ошибка команды печатается в stderr, а REPL продолжает работать.
- При `--storage=json` файл на диске никогда не остаётся в полузаписанном состоянии, даже если процесс убили посреди записи.
- Структура папок, имена пакетов, типов, функций и полей в JSON-файле — на твоё усмотрение. Тесты проверяют только поведение бинаря.

## Функциональные требования

Домен — упрощённый маркетплейс. Есть листинги, у каждого:

| Поле | Тип | Правила |
|---|---|---|
| `id` | целое | Выдаётся программой, начиная с 1. Растёт монотонно и никогда не переиспользуется, даже после удаления и после перезапуска с JSON-файлом. |
| `title` | строка | Непустая, не длиннее 200 символов. |
| `price` | число | Строго больше нуля. Печатается с двумя знаками после точки. |
| `stock` | целое | Ноль или больше. |

Бизнес-логика:

- **Создание.** Пользователь передаёт название, цену и остаток. Программа проверяет поля, присваивает следующий id и сообщает его.
- **Просмотр.** Все листинги печатаются по возрастанию id. Если листингов нет, не печатается ничего.
- **Покупка.** Пользователь указывает id и количество. Количество должно быть положительным и не больше текущего остатка. При успехе остаток уменьшается. При ошибке остаток не меняется.
- **Удаление.** Листинг удаляется по id. Его id больше никому не достанется.
- **Сохранение.** В режиме JSON после каждой изменяющей команды (add, buy, delete) всё состояние целиком записывается в файл, включая счётчик id. При следующем запуске с тем же файлом состояние восстанавливается полностью.

## Контракт

Ниже то, что проверяют тесты буквально. Формат вывода, тексты ошибок и коды возврата менять нельзя.

### Запуск

```bash
./marketplace                                   # то же, что --storage=memory
./marketplace --storage=memory
./marketplace --storage=json --file=./data.json
```

- `--storage` принимает `memory` или `json`. По умолчанию `memory`.
- При `--storage=json` флаг `--file` обязателен. Если файла нет, он создаётся пустым. Если есть, данные читаются на старте.

Программа читает stdin построчно, одна строка — одна команда. Ответы идут в stdout, ошибки в stderr. Промпт `>` печатать можно, но не обязательно: тесты срезают его с начала каждой строки.

### Команды

#### `add "<title>" <price> <stock>`

Создаёт листинг.

- Все три аргумента обязательны.
- `title` берётся в двойные кавычки. Внутри могут быть пробелы и любые символы, кроме кавычек.
- `price` — число с точкой или без: `50`, `50.00`, `30.5`.
- `stock` — целое число.
- Если аргументы не разбираются (нет кавычек, не число, не хватает аргумента), это `Error: invalid arguments`. Проверки полей (пустой title, отрицательный stock и так далее) идут после разбора.

Ответ:

```
Listing added with ID: 1
```

#### `list`

Печатает все листинги по возрастанию id, по одному на строку. Аргументов нет.

```
1. "Молоко" — 50.00 (stock: 10)
2. "Хлеб" — 30.50 (stock: 5)
```

Разделитель между названием и ценой — длинное тире `—` с пробелами по бокам. Цена всегда с двумя знаками после точки. Если листингов нет, команда не печатает ничего: ни пустой строки, ни «empty», ни «no listings».

#### `buy <id> <qty>`

Покупает `qty` штук листинга `id`.

- Оба аргумента обязательны, оба целые.
- `qty` должен быть больше нуля и не больше текущего остатка.
- Порядок проверок: сначала аргументы разбираются, потом проверяется `qty > 0`, потом существование листинга, потом достаточность остатка.
- При любой ошибке остаток не меняется.

Ответ:

```
Bought 3 of listing 1 (remaining: 7)
```

#### `delete <id>`

Удаляет листинг. Аргумент обязателен, целое число. Если листинга нет, `Error: listing not found`.

Ответ:

```
Listing 1 deleted
```

#### `exit`

Печатает `Goodbye!` и завершает программу с кодом 0. Если stdin закончился без `exit`, программа тоже должна завершиться с кодом 0.

### Полный пример сессии

```
> add "Молоко" 50.00 10
Listing added with ID: 1
> add "Хлеб" 30.00 5
Listing added with ID: 2
> list
1. "Молоко" — 50.00 (stock: 10)
2. "Хлеб" — 30.00 (stock: 5)
> buy 1 3
Bought 3 of listing 1 (remaining: 7)
> delete 2
Listing 2 deleted
> exit
Goodbye!
```

### Ошибки

Все ошибки — одна строка в **stderr** вида `Error: <message>`. Код возврата остаётся 0, программа ждёт следующую команду.

| Условие | Сообщение |
|---|---|
| Пустой title | `Error: title cannot be empty` |
| Title длиннее 200 символов | `Error: title is too long` |
| price ≤ 0 | `Error: price must be positive` |
| stock < 0 | `Error: stock must be non-negative` |
| qty ≤ 0 в `buy` | `Error: quantity must be positive` |
| Листинг с таким id не найден (buy, delete) | `Error: listing not found` |
| qty больше текущего stock | `Error: insufficient stock` |
| Неизвестная команда | `Error: unknown command '<cmd>'` |
| Не удалось разобрать аргументы | `Error: invalid arguments` |

### Хранение в JSON

- Формат файла — твой внутренний, тесты проверяют только то, что это валидный JSON.
- После каждой из команд `add`, `buy`, `delete` файл перезаписывается целиком.
- Записывай атомарно: сначала во временный файл в той же папке, потом `os.Rename` поверх основного. Тогда при падении посреди записи старый файл останется целым.
- Счётчик id тоже сохраняется. После перезапуска новый листинг получает id больше всех, что когда-либо выдавались.

## Тесты

Тесты лежат в `acceptance/`. Это чёрный ящик: они собирают твой бинарь, кормят его командами через stdin и смотрят на stdout, stderr и код возврата. Твой код они не импортируют, поэтому имена пакетов и функций им безразличны.

Что проверяется:

| Тест | Сценарий |
|---|---|
| `TestAcc01_AddAndList` | Два `add`, потом `list`. Проверяет текст ответа `add` и точный формат строк `list`. |
| `TestAcc02_ListEmptyIsSilent` | `list` на пустом хранилище не печатает ничего. |
| `TestAcc03_BuyReducesStock` | После `buy 1 3` остаток уменьшился, в ответе `remaining: 7`, в `list` виден новый stock. |
| `TestAcc04_BuyInsufficientStock` | Покупка больше остатка даёт `insufficient stock`, остаток не изменился. |
| `TestAcc05_DeleteRemovesListing` | После `delete` попытка купить тот же id даёт `listing not found`. |
| `TestAcc06_IDsDoNotReset` | Добавили два, удалили оба, добавили третий. Он получает id 3, а не 1. |
| `TestAcc07_Validation` | Восемь ошибочных вводов: пустой и длинный title, нулевая и отрицательная цена, отрицательный stock, нулевой qty, несуществующий id, неизвестная команда. Для каждого: правильное сообщение и программа не упала. |
| `TestAcc08_ErrorsGoToStderr` | Текст ошибки попал в stderr, а не в stdout. |
| `TestAcc09_ExitGoodbye` | `exit` печатает `Goodbye!` и завершает с кодом 0. |
| `TestAcc10_JSONRoundTrip` | Три запуска с одним файлом: записали и купили, перезапустили и увидели данные с правильным stock, перезапустили и получили id не меньше 3. Файл при этом валидный JSON. |

Параллельная запись в один файл из нескольких процессов не проверяется. Это отдельная тема, до неё дойдём позже.

### Как запустить

```bash
go build ./...
cd acceptance
MARKETPLACE_SRC=$(pwd)/.. go test -race -v ./...
```

Если хочешь тестировать уже собранный бинарь, укажи путь к нему вместо исходников:

```bash
MARKETPLACE_BIN=/path/to/marketplace go test -race -v ./...
```

Помимо тестов CI гоняет `gofmt`, `go vet`, `go build`, `go test -race` по твоим пакетам и `golangci-lint`. Зелёный CI означает, что задача принята.

## Правила работы с репозиторием

Код пиши в корне репозитория: `main.go` и любые пакеты рядом.

Трогать нельзя:

| Путь | Почему |
|---|---|
| `acceptance/` | Это критерий приёмки. CI сверяет содержимое с `.acceptance-manifest.sha256` при каждом запуске. |
| `.github/`, `.golangci.yml`, `.githooks/` | Инфраструктура задания. |
| Этот README | Здесь контракт. |

Эти пути закрыты через `CODEOWNERS`: PR, который их меняет, требует ревью ментора.

### Git-хуки

В репозитории лежит pre-commit хук, который перед каждым коммитом прогоняет `gofmt`, `go vet`, `go build` и проверяет, что `acceptance/` не тронут. Так ты узнаёшь о проблеме до пуша, а не из красного CI.

Git не включает хуки из репозитория сам, поэтому один раз после клонирования выполни:

```bash
make setup
```

Это просто `git config core.hooksPath .githooks`, можно и руками.

## Вопросы на собеседовании

К концу проекта на каждый вопрос нужно отвечать без подсказок. Если на каком-то залип, это и есть твоя следующая тема.

1. **Value vs pointer receiver.** У тебя есть `(s Storage) Add(...)` и `(s *Storage) Add(...)`. В каких случаях ты обязан использовать pointer receiver? Что происходит со структурой при вызове в каждом случае?
2. **Интерфейс в Go vs Java.** Чем интерфейс в Go отличается от интерфейса в Java или C#? Что такое structural typing?
3. **Nil-интерфейс.** Почему этот код печатает `not nil`? Что означает «интерфейс — это пара (type, value)»?

   ```go
   func get() error {
       var e *MyError = nil
       return e
   }
   if err := get(); err != nil { fmt.Println("not nil") }
   ```

4. **errors.Is vs errors.As.** Есть `ErrNotFound = errors.New("not found")` и тип `*ValidationError`. Когда ты используешь `errors.Is`, а когда `errors.As`? Что делает `fmt.Errorf("...: %w", err)`?
5. **Атомарная запись файла.** Почему нельзя просто `os.WriteFile` поверх существующего файла, если файл никогда не должен оказаться битым? Опиши паттерн write-rename.
6. **Деньги во float.** Почему хранить деньги в `float64` плохо? Какой тип использовать вместо него? Какое поведение твоей программы это нарушает?
7. **defer.** Три `defer` подряд в одной функции: в каком порядке они выполнятся? Если в `defer` вызывается функция с аргументами, когда вычисляются аргументы?
